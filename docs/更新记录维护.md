# 更新记录维护

欢迎页和登录后的首页右上角均有「更新记录」，对应公开页面 `/updates`。

## 每次发布

更新 `apps/web/app/updates/releases.ts`，将新版本放在数组最前面，版本号与本次发布一致。每版最多 6 条，每条只写功能名称、页面入口和一句用法；仅记录已交付功能，不写规划、内部重构或尚未上线的能力。正式发布日期可填写 `date: 'YYYY-MM-DD'`，未知则省略，不推测历史发布日期。当前 v1.0.0 条目是已有功能概览。

## Git 提交和 tag 说明

版本提交标题包含版本号和中文功能摘要，格式为 `chore(release): v1.2.3 — 按本地日期统计每周学习记录`。提交正文必须写明 `主要改动：`、`兼容边界：` 和 `测试结果：`，测试结果填写本次实际运行的命令与通过/跳过情况。注释 tag 使用 `Release v1.2.3 — 按本地日期统计每周学习记录`，并附上相同正文。

执行 `node scripts/release.mjs <版本号> --summary "中文功能摘要" --body-file <说明文件>` 发布。说明文件放在仓库外，且包含上述三个段落；脚本会拒绝缺少摘要或正文的版本提交。发布前运行 `node --test scripts/release.test.mjs`，该测试仅在临时本地 Git 仓库和 bare remote 中验证 commit/tag 消息与推送。

已推送的 v1.27.9、v1.27.10 和 v1.27.11 的提交标题与 tag 描述只包含版本号，不改写或强推历史。对应功能摘要已保留在 `apps/web/app/updates/releases.ts` 的更新记录中；从下一次发布起按上述格式生成提交和 tag 描述。

## 性能边界

- 首页入口是普通链接，不预取记录，不加载记录数据，也不增加 API、数据库请求、轮询或全局状态。
- 更新页是 Server Component，发布构建时预生成静态页面，无新增客户端交互脚本。
- 每页最多 5 个版本；历史分页同样预生成，未生成的页码返回 404。分页只有上一页和下一页，不累计渲染历史正文或全部页码。
- 记录随发布包版本保存，不调用外部更新服务。历史增长会增加构建产物总量与构建工作量，但不会让首页或单个记录页按历史总量增长。不要改成客户端一次导入全部历史、无限追加列表或定时拉取。

验证：运行 `pnpm --filter @lexloop/web typecheck`；涉及静态路由或分页时运行 Web build，确认 `/updates` 为静态页面、`/updates/[page]` 为预生成页面。
