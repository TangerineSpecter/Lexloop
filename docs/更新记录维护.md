# 更新记录维护

欢迎页和登录后的首页右上角均有「更新记录」，对应公开页面 `/updates`。

## 每次发布

更新 `apps/web/app/updates/releases.ts`，将新版本放在数组最前面，版本号与本次发布一致。每版最多 6 条，每条只写功能名称、页面入口和一句用法；仅记录已交付功能，不写规划、内部重构或尚未上线的能力。正式发布日期可填写 `date: 'YYYY-MM-DD'`，未知则省略，不推测历史发布日期。当前 v1.0.0 条目是已有功能概览。

## Git 提交和 tag 说明

版本提交标题包含版本号和中文功能摘要，格式为 `chore(release): v1.2.3 — 按本地日期统计每周学习记录`。提交正文必须写明 `主要改动：`、`兼容边界：` 和 `测试结果：`，测试结果填写本次实际运行的命令与通过/跳过情况。注释 tag 使用 `Release v1.2.3 — 按本地日期统计每周学习记录`，并附上相同正文。

执行 `node scripts/release.mjs <版本号> --summary "中文功能摘要" --body-file <说明文件>` 发布。说明文件放在仓库外，且包含上述三个段落。发布前先将验收通过的代码和文档改动明确暂存；脚本只在 `master` 上运行，只额外暂存五个版本清单，并拒绝版本号单独提交以及任何未暂存或未跟踪文件。

应用更新页与 Git 提交/tag 说明是两份不同的数据。发布脚本不会从 tag 自动生成用户说明，也不创建 GitHub Release；发布前仍需维护 `apps/web/app/updates/releases.ts`。脚本现要求该静态数组的首条版本与本次版本一致，并拒绝重复版本号、记录缺失或格式无法识别的情况。检查在写入版本清单、提交及推送之前进行，失败不会修改这些文件或引用。保留现有 `export const RELEASES: readonly Release[]` 数组声明、无引号字段名及字符串/数组/对象字面量格式；不使用动态表达式或展开项。解析会忽略注释并区分字符串，不执行 TypeScript 内容，同时核对每版有 1–6 条完整功能说明。

v1.27.153 至 v1.27.172 的提交和注释 tag 已有说明，但应用更新记录漏维护，曾停在 v1.27.152。本次根据对应 tag 补齐这 20 版的用户说明，不改写已推送的提交或标签；默认关闭、需显式运维操作的能力仍明确保留这些边界。

检查器仅支持文件现有的 `Release` 类型定义和末尾两条分页常量，拒绝其他前后置执行代码、模板字符串与转义版本号。若重构数据格式、类型或分页常量，需同步更新检查器及测试，而不是绕过发布检查。

发布前运行 `node --test scripts/release.test.mjs`。测试在临时本地 Git 仓库和 bare remote 中验证提交/tag 消息、master 与标签引用、版本号单独提交拒绝、未跟踪文件隔离和分支限制，不会改动真实远端。

测试还覆盖旧记录、版本顺序错误、重复版本、文件缺失及注释伪声明，确认拒绝发布时五个版本清单、本地与远端 master/tag 及暂存内容保持原样。静态解析测试覆盖注释与字符串中的示例文本、重复字段、动态表达式、展开项、空说明及真实历史记录范围。

已推送的 v1.27.9、v1.27.10 和 v1.27.11 的提交标题与 tag 描述只包含版本号，不改写或强推历史。对应功能摘要已保留在 `apps/web/app/updates/releases.ts` 的更新记录中；从下一次发布起按上述格式生成提交和 tag 描述。

## 性能边界

- 首页入口是普通链接，不预取记录，不加载记录数据，也不增加 API、数据库请求、轮询或全局状态。
- 更新页是 Server Component，发布构建时预生成静态页面，无新增客户端交互脚本。
- 每页最多 5 个版本；历史分页同样预生成，未生成的页码返回 404。分页只有上一页和下一页，不累计渲染历史正文或全部页码。
- 记录随发布包版本保存，不调用外部更新服务。历史增长会增加构建产物总量与构建工作量，但不会让首页或单个记录页按历史总量增长。不要改成客户端一次导入全部历史、无限追加列表或定时拉取。

验证：运行 `pnpm --filter @lexloop/web typecheck`；涉及静态路由或分页时运行 Web build，确认 `/updates` 为静态页面、`/updates/[page]` 为预生成页面。
