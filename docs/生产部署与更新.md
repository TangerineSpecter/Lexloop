# Lexloop 生产部署与更新

本文适用于单台 Linux x86_64 服务器，建议至少 2 核 CPU、4 GB 内存和 40 GB SSD。当前方案面向局域网 IP 访问，使用 Docker Compose 在服务器本地按 Git tag 构建应用镜像，不依赖 GHCR。

## v1.0.0–v1.0.2 安装故障恢复

这些版本存在 API 编译入口错位和 updater 启动入口冲突。若安装中断、API unhealthy 或后台显示「更新服务未连接」，在用于获取安装脚本的仓库中拉取最新代码，再执行：

```bash
git pull --ff-only origin master
sudo ./deploy/install.sh v1.0.3
```

脚本复用 `/opt/lexloop` 的生产配置和数据库卷；不需要删除容器卷、重新注册或手工修改发布 worktree。不要继续执行旧 checkout 中的安装脚本。已有业务数据时，修复前建议先执行 `/opt/lexloop/backup.sh`（若已安装）保存备份。

从 v1.0.3 起，安装会等待 updater 与应用容器健康，检查首页、API 版本以及 API 到 updater 的 socket 连接，并注册备份计划；全部通过才显示部署完成。失败会报告阶段和容器状态，可以在排除原因后重新执行安装。需要支持 `docker compose up --wait` 的 Compose V2 插件。

开发时运行 `pnpm test:deploy` 检查安装成功/失败阶段、更新状态响应、版本检查、切换恢复和 updater 自更新流程；API 构建与运行仍需使用真实镜像验证，不能仅以脚本测试通过作为发布依据。

API 使用独立生产编译配置，镜像构建会检查 API、Worker 入口和词表资源，构建与运行镜像均提供 Prisma 所需 OpenSSL。updater 使用 Node 22 Debian 运行时并复制 Docker CLI/Compose/Buildx 插件，显式清除基础镜像入口。

## 发布前准备

生产部署只接受以下版本：

- 名称符合 `v主版本.次版本.修订号` 的稳定版本，例如 `v1.0.0`；
- annotated tag，不接受 lightweight tag；
- tag 对应提交必须位于 `origin/master`；
- 根目录及所有 workspace 的 `package.json` 版本必须和 tag 一致。

首次发布前在开发机完成：

```bash
pnpm typecheck
pnpm test
pnpm build
pnpm release 1.0.0
```

`pnpm release` 会提交当前工作区的全部改动、推送当前分支并创建或移动远端 tag。执行前务必检查 `git status`，确认没有密钥、本地数据或无关文件。

## 首次安装

服务器需预装并启动 Docker Engine、Docker Compose plugin、Git、OpenSSL 和 curl。不要在生产机安装 GitHub self-hosted runner。

先在服务器取得对应版本的安装脚本并检查内容：

```bash
git clone --depth 1 https://github.com/TangerineSpecter/Lexloop.git /tmp/lexloop-installer
cd /tmp/lexloop-installer
sudo ./deploy/install.sh
```

不传版本号时，脚本会自动选择 `master` 上最新、可验证的稳定 annotated tag。若必须固定首次部署版本，可传入版本参数，例如 `sudo ./deploy/install.sh v1.2.0`。

首次安装的网关端口默认为 `12880`，避免占用常见的 HTTP `80` 端口。也可以显式指定端口，版本号和端口参数可同时使用：

```bash
sudo ./deploy/install.sh --port 12881
sudo ./deploy/install.sh v1.2.0 --port 12881
```

重新安装默认保留 `production.env` 中已有的端口（包括旧安装的 `80`），只有显式传入 `--port` 或 `HTTP_PORT` 环境变量时才覆盖。脚本会在构建镜像前检查端口是否被其他服务占用，并提示选择其他端口。更换端口不会改变 API 容器内的 `52101`；对外端口由 Caddy 网关统一提供。

脚本是幂等的，会执行以下操作：

1. 在 `/opt/lexloop` 初始化裸 Git 仓库、版本 worktree、配置、状态和备份目录。
2. 生成 PostgreSQL、MinIO、JWT 和 AI 配置加密密钥，保存到权限为 `600` 的 `/opt/lexloop/config/production.env`。
3. 利用 BuildKit/pnpm 缓存构建 Web、API、Worker 和迁移镜像。
4. 启动 PostgreSQL、Redis，执行 `prisma migrate deploy`，再启动应用、Caddy 和独立 updater。
5. 验证 API 返回的版本和 commit SHA，安装每天 03:17 执行的数据库备份计划。

默认入口为：

```text
http://服务器局域网IP:12880/
```

数据库、Redis 和可选 MinIO 不映射宿主机端口。首次启动使用全新数据库，请立即注册第一个账号；现有注册事务保证第一个账号成为唯一 `ADMIN`。在首账号注册完成前，不要把该入口反向代理到公网。

## 配置与 HTTPS

生产配置位于 `/opt/lexloop/config/production.env`。局域网 HTTP 模式保留：

```dotenv
WEB_ORIGIN=http://localhost:12880
COOKIE_SECURE=false
HTTP_PORT=12880
```

首次下载 Docker Hub 基础镜像较慢时，可在执行安装脚本前配置 Docker daemon 的 registry mirror；也可以先让脚本生成 `production.env`，把其中 `NODE_IMAGE`、`DOCKER_CLI_IMAGE`、`POSTGRES_IMAGE`、`REDIS_IMAGE`、`CADDY_IMAGE` 改成可信镜像站的完整地址后重新执行。后续构建会复用本机基础层和 pnpm BuildKit 缓存。

如果直接通过服务器 IP 访问，应把 `WEB_ORIGIN` 设置为实际地址（含端口），例如 `http://192.168.1.10:12880`。`--port` 只会同步默认的 localhost 来源地址，保留用户已配置的域名或 IP；更改端口后也需检查该自定义地址。

如果以后通过宝塔、Caddy 或其他代理使用 `https://lexloop.example.com`，需要把 `WEB_ORIGIN` 改为真实 HTTPS 地址，并将 `COOKIE_SECURE` 改为 `true`。外层代理转发到服务器的 `HTTP_PORT`（默认 `12880`）即可；不要代理 PostgreSQL、Redis、MinIO 控制台或 updater。

如由本项目 Caddy 直接终止 HTTPS，可参考 `deploy/Caddyfile.https.example`，配置域名、管理员邮箱和 443 端口后重新创建 gateway。

## 后台检查与更新

唯一管理员进入“设置 → 系统设置 → 系统更新”即可检查和安装版本。updater 每 6 小时也会检查一次，但不会自动安装。

版本判断同时比较 SemVer 和 commit SHA：

- 新版本号指向当前提交的后继提交时，可以更新；
- 同名 tag 被移动到新的后继提交时，显示“同版本修订”；
- tag 指向旧提交、分叉提交、预发布版本或版本号不一致时拒绝更新。

点击“立即更新”后需要重新输入当前管理员密码。最近一次任务成功后，页脚会显示「重新载入」；若此时仍有可安装的新版本，「立即更新」与「重新载入」同时出现，不会被成功状态隐藏。流程为：重新校验 tag → 独立 worktree → Compose 配置检查 → 缓存构建 → PostgreSQL 备份 → Prisma migration → 切换容器 → Web/API/版本健康检查。

版本检查的 Git 拉取异步执行，最长 60 秒，同一时刻的检查合并执行，不阻塞状态查询；API 为手动检查保留 75 秒等待时间。容器部分切换后失败也会尝试恢复上一版应用镜像，数据库迁移不会自动回滚。应用与 updater 镜像都在切换前构建；更新完成后由独立的一次性容器刷新 updater，避免更新服务替换自身时中断 Compose 子进程。

应用切换失败时 updater 会恢复上一版 Web/API/Worker 镜像。数据库不会自动恢复，因此 migration 必须遵循 expand/contract：先新增兼容字段或表，待所有运行版本不再依赖旧结构后，才在后续版本删除旧结构。

常用诊断命令：

```bash
docker logs --tail 200 lexloop-updater
docker logs --tail 200 lexloop-gateway
docker compose --project-name lexloop --env-file /opt/lexloop/config/production.env \
  --file "$(grep '^CURRENT_RELEASE_PATH=' /opt/lexloop/config/production.env | cut -d= -f2)/deploy/compose.prod.yml" ps
```

updater 的任务状态保存在 `/opt/lexloop/data/updater/update-state.json`。日志会限制长度并隐藏密码、令牌和密钥，updater 只监听 Unix Socket，不开放 TCP 端口。

## 备份与恢复

系统每次更新前创建备份，每天另存一个日备份：

```text
/opt/lexloop/backups/daily
/opt/lexloop/backups/weekly
```

默认保留 7 个日周期和 4 个周周期。建议在 `/opt/lexloop/config/backup-sync` 放置一个仅 root 可执行的同步脚本，将新备份复制到另一台机器或 NAS；备份脚本会把新备份路径作为第一个参数传入。

手动创建备份：

```bash
sudo /opt/lexloop/backup.sh
```

灾难恢复前先保留当前数据库并停止写入服务，再恢复指定备份：

```bash
source /opt/lexloop/config/production.env
release_compose="$CURRENT_RELEASE_PATH/deploy/compose.prod.yml"
docker compose --project-name lexloop --env-file /opt/lexloop/config/production.env \
  --file "$release_compose" stop web api worker
docker exec lexloop-postgres dropdb --force -U "$POSTGRES_USER" "$POSTGRES_DB"
docker exec lexloop-postgres createdb -U "$POSTGRES_USER" "$POSTGRES_DB"
docker exec -i lexloop-postgres pg_restore -U "$POSTGRES_USER" -d "$POSTGRES_DB" \
  --clean --if-exists < /opt/lexloop/backups/daily/要恢复的备份.dump
docker compose --project-name lexloop --env-file /opt/lexloop/config/production.env \
  --file "$release_compose" up -d web api worker gateway
```

恢复必须先在非生产环境演练。数据库备份不包含未来 MinIO 对象；启用文件上传后，需要另外备份 `minio_data` 或使用外部 S3/NAS 的版本管理。

## SFTP 远端备份与整机故障恢复

管理员在「系统设置 → 远端备份」配置。普通用户看不到系统设置，所有备份管理接口另有 JWT 与 ADMIN 权限检查；保存配置和手动执行还需复验当前管理员密码。生产运维镜像必须更新到包含此功能的版本，旧版 updater 或本地开发未启动 updater 时显示服务未连接。

配置文件损坏或生产加密密钥更换导致无法解密时，页面会明确显示配置错误，仍允许管理员填写完整配置。勾选「确认用下方完整配置替换无法解密的旧配置」，重新输入 SSH 私钥、备份解密口令及管理员密码后保存；不会保留或读取损坏配置中的旧凭据。原远端备份不受替换影响，仍需各自原来的解密口令。状态文件写入失败会显示磁盘/权限错误并释放运行锁，避免阻断后续备份和系统更新。

远端服务器准备一个专用账号和可写目录，将专用 SSH 公钥加入该账号的 `authorized_keys`。页面填写主机、端口、用户名、绝对目录、**服务器主机公钥**（例如 `ssh-ed25519 AAAA…`，由远端管理员从 `/etc/ssh/ssh_host_ed25519_key.pub` 获取并通过可信渠道核对）、未加密的客户端 SSH 私钥，以及至少 16 位的备份解密口令。当前支持 SSH 私钥认证，不支持 SSH 密码或需要交互解锁的私钥。目录只支持字母、数字、点、横线、下划线和 `/`，需要提前创建。

**把备份解密口令保存在另一台设备或密码管理器中。** 不要只保存在被备份的服务器上；丢失口令就无法恢复远端备份。更改口令不会重新加密旧文件，旧口令也要保留。

启用后，独立 updater 每分钟检查计划，距上次成功满 24 小时执行一次，首次启用会在下一次检查时执行。失败后至少间隔一小时重试；系统更新和远端备份互斥，重启会把中断的备份标记为失败。管理员可立即备份并查看最近尝试、成功时间、文件名及错误；超过 26 小时没有成功会显示提醒。这些提醒展示在系统设置内，目前不发送邮件或站外通知。关闭自动备份仍可手动执行。

每次任务使用 `pg_dump -Fc` 创建 PostgreSQL 一致性快照，并与 `production.env`、版本清单打包，用独立口令通过 scrypt + AES-256-GCM 加密后上传。先写 `.partial`，上传完成才重命名为 `.lxbackup`；只有重命名成功才记录成功。本地临时文件在任务结束时删除。SSH 私钥与解密口令使用生产 `AI_CONFIG_ENCRYPTION_KEY` 加密保存在 `/opt/lexloop/config/remote-backup.enc`，接口不会返回明文。备份使用严格的 SSH 主机公钥校验；主机换钥后需重新核对并保存。

远端每次生成独立文件，**不自动清理历史**。请在备份服务器配置保留策略、磁盘容量和权限；建议保留最近 7 天及至少 4 个周版本，另行清理长期残留的 `.partial`。原有本地日/周备份及 `backup-sync` 扩展保持有效，独立的远端计划不依赖宿主机安装 SFTP 客户端。

备份覆盖用户、学习记录、系统配置、已生成内容及模型密钥。它不包含 Redis/BullMQ 未完成队列、MinIO 对象、网关证书或自定义部署文件。启用文件上传或自定义网关后须另行备份对应资源；恢复后应检查并重试未完成的业务任务。

### 仅凭远端文件恢复

1. 从远端取回指定 `.lxbackup`，在安全的新服务器取得项目代码（包含 `deploy/backup/decrypt.mjs`），安装 Node.js 22+。恢复不依赖原机器或其加密密钥。
2. 在 Bash 中读取独立保管的口令，从标准输入交给工具，避免把口令放入命令参数或命令历史：

   ```bash
   umask 077
   read -r -s -p '备份解密口令: ' lexloop_backup_passphrase
   printf '\n'
   printf '%s' "$lexloop_backup_passphrase" | node deploy/backup/decrypt.mjs \
     /安全目录/lexloop-指定版本.lxbackup /安全目录/recovered.tar.gz
   unset lexloop_backup_passphrase
   mkdir -m 700 /安全目录/recovered
   tar -xzf /安全目录/recovered.tar.gz -C /安全目录/recovered
   ```

   工具验证格式与 GCM 完整性，口令错误或文件损坏会失败并清除未完成的输出，不覆盖已存在的输出文件。解压得到 `database.dump`、`production.env` 和 `manifest.json`。

3. 查看清单及原配置中的版本，先在隔离环境部署**备份对应的相同 tag/commit**，不要先用旧备份覆盖新版数据库。新安装在受限网络下进行，恢复完成前不要开放注册。新服务器保留自己的 `CURRENT_RELEASE_PATH`、镜像及部署版本路径；将原配置的 `AI_CONFIG_ENCRYPTION_KEY`、JWT 密钥、数据库账号密码及必要业务配置合并到新 `production.env`（权限 `600`），按新地址调整 `WEB_ORIGIN`、端口与 HTTPS。不要把旧机器的整份环境文件直接覆盖到不同路径的新部署。
4. 停止 Web/API/Worker，使用上节数据库恢复流程导入 `database.dump`，重新创建服务使新配置生效。确认管理员登录、学习记录、模型调用及版本健康检查后再切换域名或访问入口。升级到新版应在恢复验证后进行。
5. 在系统设置重新配置 SFTP，并执行一次远端备份。远端认证信息刻意不包含在恢复包里，需要重新准备；原备份解密口令可继续使用，也可换新并保留旧口令。安全删除恢复产生的明文压缩包及配置文件。

对迁移要求不丢失最后一笔写入时，须安排维护窗口、停止旧机写入并制作最终备份；每日备份可能损失最近一次成功备份之后的数据。上线前应在另一台机器实际演练数据库恢复，不能仅以上传成功判断整个系统可恢复。
